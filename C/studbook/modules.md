# Модульное программирование в языке C

В процессе разработки крупных программ сложно поддерживать весь код в одном файле. Это приводит к запутанности, трудностям в отладке и невозможности повторного использования кода. Для решения этих проблем используется **модульное программирование**.

## Что такое модуль?

**Модуль** — это логически завершенная часть программы, которая выполняет определенную задачу (например, работа с математическими функциями, обработка строк или управление файлами). 

Основная идея модульности заключается в разделении программы на компоненты, которые взаимодействуют друг с другом через четко определенный **интерфейс**, скрывая свою внутреннюю реализацию.

## Анатомия модуля: Заголовочные и исходные файлы

В языке C модуль обычно состоит из файлов двух типов: заголовочного файла `.h` и файла исходного кода `.c`.

### 1. Заголовочный файл (`.h`) — Интерфейс

Заголовочный файл описывает **что** модуль умеет делать. Он служит "витриной" или "контрактом" между модулем и остальной частью программы. Можно говорить, что это аналог раздела `interface` модуля Паскаля.

**Что обычно содержится в `.h` файлах:**
* **Объявления функций**, которые можно вызывать из других файлов.
* **Определения типов.** `typedef`, `struct`, `enum`.
* **Макросы:** `#define` и другие.
* **Внешние переменные:** Объявления через `extern`.

> **Важно:** Заголовочный файл не должен содержать *реализацию* (тело) функций, только их *объявления* (declaration).


### 2. Файл исходного кода (`.c`) — Реализация

Описывает **как** модуль выполняет свои задачи. Здесь содержится исполняемый код.

**Что обычно содержится в `.c` файлах:**
* **Определения (definition) функций:** Тела функций, объявленных в заголовочном файле.
* **Локальные (для модуля) элементы.** Переменные и вспомогательные функции, которые нужны только внутри этого модуля и не должны быть видны снаружи.



## Инкапсуляция и сокрытие данных

Одним из главных преимуществ модулей является **информационная скрытость** (information hiding). Мы можем скрыть детали реализации, чтобы пользователь модуля не мог случайно нарушить внутреннее состояние модуля или зависеть от деталей, которые могут измениться.

* **Открытый интерфейс** -- что объявлено в `.h`.
* **Закрытая реализация:** -- что определено в `.c`, но не объявлено в `.h`.


## Пример модуля

Представим модуль для работы с простыми математическими операциями.

#### `math_utils.h` (Интерфейс)
```c
#pragma once

/**
 * Возвращает сумму двух целых чисел.
 */
int add(int a, int b);

/**
 * Возвращает квадрат числа.
 */
int square(int x);
```


### `math_utils.c` (Реализация)
```c
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}

int square(int x) {
    return x * x;
}
```


### `main.c` (Использование)
```c
#include <stdio.h>
#include "math_utils.h"

int main() {
    int sum = add(5, 3);
    int sq = square(4);

    printf("Sum: %d\n", sum);
    printf("Square: %d\n", sq);

    return 0;
}
```

#### Компиляция многомодульного проекта

Собрать проект из нескольких `.c` файлов можно двумя способами.

**Вариант 1: раздельная компиляция**

Сначала компилируются файлы модулей. Потом основная программа. Это может ускорить компиляцию, если чаще всего меняется основная программа, а большую часть модулей не требуется перекомпилировать.

Но такой поход требует нескольких команд компиляции:

```bash
# Шаг 1 — компилируем каждый .c файл в объектный (.o)
gcc -c math_utils.c -o math_utils.o
gcc -c main.c -o main.o

# Шаг 2 — линкуем объектные файлы в исполняемый
gcc main.o math_utils.o -o program
```

Такой подход эффективен при частых пересборках. После изменения одного файла перекомпилируется только он, а остальные `.o` переиспользуются.

**Вариант 2: одной строкой командой**

```bash
gcc main.c math_utils.c -o program
```

Компилятор сделает то же самое, но без сохранения промежуточных объектных (`.o`) файлов (скомпилированных файлов модулей).



## `extern` — общие переменные между модулями

Иногда в модуле нужно объявить глобальную переменную, котора будет доступна не только в рамках текущего модуля но и в других файлах исходного кода. Для этого в C используется ключевое слово `extern`.

### Как это работает

- **Объявление (declaration) переменной с ключевым словом `extern`** — сообщает компилятору: эта переменная где-то существует, но определена в другом файле.
- **Определение (definition) переменной** — выделяет память под переменную. Определение должно быть ровно одно (во всём проекте).

### Пример

```c
// logger.h
#pragma once

extern int log_level;          // <-- объявление: переменная определена в .c

void log_message(const char* msg);
```

```c
// logger.c
#include "logger.h"

int log_level = 2;             // <-- определение: реальная память

void log_message(const char* msg) {
    if (log_level > 0) {
        printf("[LOG] %s\n", msg);
    }
}
```

```c
// main.c
#include "logger.h"

int main() {
    log_level = 3;              // меняем глобальную переменную модуля
    log_message("Старт");
    return 0;
}
```

> ⚠️ **Золотое правило:** объявление с `extern` помещается в `.h` (интерфейс), а определение — строго в один `.c` (реализация). Никогда не определяйте переменную в заголовочном файле — иначе при включении этого `.h` из нескольких `.c` файлов компоновщик выдаст ошибку `multiple definition` — множественно объявление переменной.


## `static` — сокрытие внутри модуля

Ключевое слово static в языке C имеет несколько вариантов использования. Они зависят от контекста.

Ключевое слово `static` на уровне файла делает функцию или переменную **видимой только внутри этого файла**. Это главный механизм сокрытия внутренних деталей реализации.

### Статические функции

Если вспомогательная функция нужна только внутри модуля — объявите её `static`. Она не попадёт в таблицу символов компоновщика, и другой модуль не сможет её вызвать (даже случайно).

```c
// math_utils.c
#include "math_utils.h"

// Приватная функция — доступна только внутри этого файла
static int is_positive(int x) {
    return x > 0;
}

int add(int a, int b) {
    return a + b;
}

int square(int x) {
    // даже при отрицательном x вернём квадрат
    return x * x;
}
```

Попытка вызвать `is_positive` из `main.c` приведёт к ошибке компоновки (`undefined reference`).

### Статические переменные

`static` на переменной уровня файла создаёт **глобальную переменную, видимую только внутри этого файла**. В отличие от `extern`-переменных, она не объявляется в `.h` и полностью скрыта от внешнего мира.

```c
// counter.c
#include "counter.h"

static int call_count = 0;    // видна только внутри counter.c

int get_count(void) {
    return call_count;
}

void increment(void) {
    call_count++;
}
```

Итоговая таблица по видимости:

| Объявление | Где помещается | Видимость |
|---|---|---|
| `extern int x;` | `.h` (интерфейс) | Весь проект |
| `int x = 0;` (определение) | один `.c` | Весь проект |
| `static int x = 0;` | `.c` | Только этот `.c` |
| `static void f(void);` | `.c` | Только этот `.c` |


## Структура папок и подключение файлов

В реальных проектах, где много файлов исходного кода, их не сохраняют в одну папку, а распределяют по разным папкам.

Это может быть структура вида:
- `include/` -- папка с `.h` файлами 
- `src/` -- папка с `.c`

Иногда имеет смысл создавать отдельные подпапки для групп модулей. Например:
- `data` -- подпапка с модулями (.h и .c файлы) для обработки данных;
- `io` -- подпапка с модулями, отвечающими за ввод и вывод
- `graphics` -- подпапка для модулей, отвечающих за графику.
- и т.п.

Можно также объединить описанные выше подходы.


### Подключение файлов из папок
Пример структуры проекта:
```
project/
├── graphics/ 
│   ├── my_graphics.h
│   └── my_graphics.c
├── main.c
```

Подключение файла в main.c:
```c
#include "graphics/my_graphics.h"
```


### Общий путь к заголовочным файлам

Когда `.h` лежат в отдельной папке, стоит сообщить компилятору, где их искать:

```bash
# Флаг -I добавляет директорию в путь поиска #include
gcc -c src/main.c -I include -o main.o
gcc -c src/math_utils.c -I include -o math_utils.o
gcc main.o math_utils.o -o program
```

Внутри `.c` файлов заголовки подключаются так:

```c
// src/main.c
#include <stdio.h>          // системный заголовок — ищется в /usr/include и т.д.
#include "math_utils.h"    // пользовательский — ищется в -I директориях
```

> **Разница между `< >` и `" "`:**
> - `#include <file.h>` — поиск только в системных директориях (и флагах `-I`).
> - `#include "file.h"` — сначала поиск в той же папке, где лежит текущий `.c`, затем в `-I` директориях.



### Подключение внутри заголовков

Если один `.h` использует типы из другого `.h`, он должен его включить (include). При этом важна самодостаточность: каждый `.h` должен компилироваться сам по себе.


```c
// include/vec2.h
#pragma once

#include "math_utils.h"    // нужно, потому что используется тип Point

typedef struct {
    int x;
    int y;
    Point center;           // Point объявлен в math_utils.h
} Vec2;
```

## Практические рекомендации и лучшие практики (best practices)

### 1. Защита от повторного включения (include guard)

Когда один заголовочный файл включает другой, может возникнуть ситуация, когда одно и то же объявление встречается несколько раз, что приведет к ошибке компиляции. 

**Пример правильного `.h` файла:**

```c
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

// Все объявления здесь
int add(int a, int b);

#endif // MATH_UTILS_H
```

`#pragma once` -- нестандартная, но более простая и широко поддерживаемая директива компилятора, защищающая от повторного включения (include) файлов:

```c
#pragma once

// Все объявления здесь
int add(int a, int b);

```

### 2. Не включайте `.c` файлы

Никогда не делайте `#include "module.c"`. Это нарушает принцип раздельной компиляции и приводит к ошибкам линковки (компоновки). Вместо этого включайте только `.h` файлы.

### 3. Минимизируйте зависимости в заголовках

Старайтесь включать в заголовочный файл только те файлы, которые действительно необходимы для понимания его интерфейса. Это ускоряет компиляцию и уменьшает связность кода.




**Общий порядок сборки**
1. Компилятор превращает `math_utils.c` в объектный файл `math_utils.o`.
2. Компилятор превращает `main.c` в объектный файл `main.o`.
3. Линковщик (linker) соединяет `main.o` и `math_utils.o` в единый исполняемый файл.
